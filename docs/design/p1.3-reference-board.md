# P1.3 Five-Scene Reference Board

> 采集范围：为“问得更好”五幕 Question Compiler 收集视觉与交互参考。
>
> 采集时间：2026-09-14。
>
> 使用边界：只采视觉语言、节奏、层级和交互反馈；不复制品牌资产，不引入大图、WebGL、3D 或滚动劫持。主业务阶段仍由 React 管理，GSAP 只负责视觉表现。

## A. Scene Transition

### 01. GSAP Timeline
- 来源：[GSAP Timeline 文档](https://gsap.com/docs/v3/GSAP/Timeline/)
- 描述：用 timeline、label 和 position parameter 编排多个动画的先后与重叠关系。
- 采：用可读的 timeline 组织 Backdrop → Stage number → Headline → Main content 的 Push + Reveal 节奏。
- 不采：不用 timeline 改写 React stage、API loading 或导航状态；不把每个元素做成独立长动画。
- 对应：Shared / Input → Clarify → Diagnose → Coverage → Result

### 02. GSAP matchMedia
- 来源：[GSAP matchMedia 文档](https://gsap.com/docs/v3/GSAP/gsap.matchMedia%28%29/)
- 描述：按 viewport 条件和 `prefers-reduced-motion` 建立可自动回退、可清理的动画上下文。
- 采：Desktop 与 Mobile 使用不同位移和时长；reduce motion 时切换到短 fade。
- 不采：不让媒体查询决定业务 stage；不在服务端执行 GSAP。
- 对应：Shared / Responsive / Accessibility

### 03. GSAP ScrollTrigger
- 来源：[GSAP ScrollTrigger 文档](https://gsap.com/docs/v3/Plugins/ScrollTrigger/)
- 描述：展示 horizontal panels、scrub、pin 等滚动关联的空间和边界语言。
- 采：只参考 panel 边界、横向接管、背景与内容连续性的视觉感觉。
- 不采：不使用 ScrollTrigger 驱动 Input → Clarify → Diagnose → Coverage → Result 主流程，不做滚动劫持。
- 对应：Shared / Scene transition reference only

### 04. Material Motion
- 来源：[Material Motion](https://m1.material.io/motion/material-motion.html)
- 描述：强调 motion 应表达空间关系、功能和意图，并保持单一环境中的连续性。
- 采：阶段切换时保持同一 Question Compiler 空间，让背景、内容和方向共同传达“正在编译”。
- 不采：不照搬 Material 的 surface、elevation 或物理拟态样式。
- 对应：Shared / Scene transition

### 05. View Transitions API
- 来源：[MDN View Transitions API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transitions_API)
- 描述：关注状态切换中的连续视觉过渡，以及内容更新与视觉过渡的分离。
- 采：参考“旧内容退场、新内容接管”的连续感和不闪烁原则。
- 不采：不替换现有 React 状态模型，不把浏览器 View Transition 当成业务流程控制器。
- 对应：Shared / Scene viewport

### 06. Chrome View Transitions
- 来源：[Chrome View Transitions 指南](https://developer.chrome.com/docs/web-platform/view-transitions)
- 描述：从 Web 平台角度说明页面状态之间的平滑过渡和渐进增强思路。
- 采：参考在不改变 DOM 语义的前提下建立 transition boundary。
- 不采：不为兼容性引入额外路由框架或全屏遮罩，不牺牲表单和焦点行为。
- 对应：Shared / Backdrop and viewport boundary

## B. Typography

### 07. Apple Typography
- 来源：[Apple Human Interface Guidelines — Typography](https://developer.apple.com/design/human-interface-guidelines/typography)
- 描述：强调可读性、字号/字重层级、动态字体适配和减少字体混用。
- 采：建立阶段编号、标题、正文、辅助信息的稳定层级；保留足够行距和高对比度。
- 不采：不使用过细字重，不为了“编辑感”压缩中文正文行高。
- 对应：Shared / Stage number and headline

### 08. Material Typography
- 来源：[Material 3 Typography](https://m3.material.io/styles/typography/overview)
- 描述：把 typography 作为可复用的 display、headline、body、label 角色系统。
- 采：用有限的文字角色支持五幕层级，避免每幕单独发明字号体系。
- 不采：不整套引入 Material 组件、字体或默认色板。
- 对应：Shared / Typography tokens

### 09. Carbon Typography
- 来源：[IBM Carbon Typography](https://carbondesignsystem.com/elements/typography/overview/)
- 描述：提供面向产品界面的类型尺度、字重和内容层级参考。
- 采：参考信息密集的 Diagnose、Coverage 场景如何用 label、body、heading 拉开层级。
- 不采：不复制 Carbon 的品牌字体、组件外观或企业后台气质。
- 对应：Diagnose / Coverage

### 10. Geist Font
- 来源：[Vercel Geist Font](https://vercel.com/font)
- 描述：以简洁的无衬线字体和清晰的文本层级支撑产品界面。
- 采：参考克制的 sans-serif 质感、标题与正文的清楚分工、较大的留白。
- 不采：不把 Vercel 的黑白品牌系统或字标带入“问得更好”。
- 对应：Shared / Input and Result typography

### 11. GSAP SplitText
- 来源：[GSAP SplitText 文档](https://gsap.com/docs/v3/Plugins/SplitText/)
- 描述：提供按行、词、字符拆分文本并进行 reveal 的能力示例。
- 采：只采 mask reveal、line stagger 的节奏启发；优先用现有 DOM + CSS overflow + timeline 实现。
- 不采：本轮不安装或依赖 SplitText，不做逐字弹跳，不让文字动画延迟可读内容。
- 对应：Shared / Stage number, headline, Result Before → After

### 12. Fluid Typography
- 来源：[CSS-Tricks Fluid Typography](https://css-tricks.com/snippets/css/fluid-typography/)
- 描述：讨论利用 viewport 和 `clamp()` 让字号在不同屏幕平滑变化。
- 采：参考 Desktop 1440 到 Mobile 390 的标题缩放和安全换行边界。
- 不采：不让标题无限放大，不用 fluid 计算破坏中文可读性和按钮布局。
- 对应：Input / Result / Responsive typography

## C. Product Interaction

### 13. Linear UI Refresh
- 来源：[Linear — A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)
- 描述：围绕信息密度、视觉降噪、导航层级和一致性进行界面刷新。
- 采：让辅助导航退后，把当前工作区和主要 CTA 放在视觉中心；用小细节提升连续体验。
- 不采：不复制 Linear 的图标、配色、圆角或品牌布局。
- 对应：Shared / Stepper and primary workspace

### 14. Linear Brand Guidelines
- 来源：[Linear Brand Guidelines](https://linear.app/brand)
- 描述：展示留白、单色标识、色彩使用和品牌资产留出空间的原则。
- 采：参考“让元素呼吸”的留白和克制的辅助信息密度。
- 不采：不使用 Linear logo、wordmark、品牌色或其视觉资产。
- 对应：Shared / Header and navigation restraint

### 15. Vercel Geist
- 来源：[Vercel Geist Design System](https://vercel.com/geist)
- 描述：提供产品型界面的组件、颜色、排版和交互规范入口。
- 采：参考清晰边界、低噪声 surface、明确 focus 和状态反馈。
- 不采：不把单色黑白界面直接套在五幕色板上，不引入 Geist 组件依赖。
- 对应：Shared / Buttons, input, surfaces

### 16. Raycast
- 来源：[Raycast](https://www.raycast.com/)
- 描述：以快速命令、即时反馈和高信息密度构成效率工具的交互参考。
- 采：参考短反馈、明确选中态、低延迟的 loading 和键盘友好焦点。
- 不采：不复制 Raycast 的 launcher、命令面板或暗色产品壳。
- 对应：Clarify / Selection and keyboard focus

### 17. Notion
- 来源：[Notion Product](https://www.notion.so/product)
- 描述：内容优先、块级组织和渐进展开的产品交互参考。
- 采：参考让信息按需出现、保留用户回看和修改路径、减少一次性认知负担。
- 不采：不引入块编辑器、不改变现有问答表单结构、不隐藏关键证据。
- 对应：Clarify / Coverage progressive disclosure

### 18. Perplexity
- 来源：[Perplexity](https://www.perplexity.ai/)
- 描述：搜索与回答结合的产品入口，强调问题输入、来源和回答结果的连续关系。
- 采：参考证据链接的可见性、结果优先级和“来源支持结论”的信息关系。
- 不采：不复制 Perplexity 的品牌语言、搜索产品布局或 AI 回答内容。
- 对应：Coverage / Result evidence and source links

### 19. Arc
- 来源：[Arc Browser](https://arc.net/)
- 描述：以空间化导航、轻量反馈和带有个性的微交互形成产品体验。
- 采：参考 hover、press 和导航切换的轻微位移与节奏差。
- 不采：不复制浏览器侧栏、彩色标签系统或品牌插画，不做过度装饰。
- 对应：Shared / Button and navigation micro-interactions

## Synthesis

- **主基调**：编辑型叙事的章节感 + 产品型交互的可用性；不是展示型 landing page。
- **切换方式**：采用 Push + Reveal 的连续换幕；ScrollTrigger 只作为视觉参考，不进入主业务状态机。
- **文字方式**：有限的 typography roles、mask reveal 和短 stagger；内容必须迅速可读。
- **产品边界**：保留 loading、error、back/revisit、evidence links、copy、reoptimize、new question 以及 answer invalidation。
- **资源边界**：CSS/SVG-like 几何优先；不下载或打包大图片，不做 WebGL、3D 或大范围 blur。
