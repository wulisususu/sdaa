# P1.3.1 Scene Continuity & One-Viewport Visual Refinement Design

> Status: **Design only**. This document defines the next visual/interaction refinement phase. It does **not** authorize changes to AI prompts, provider logic, API contracts, Domain schemas, Zhihu retrieval, compilation, semantic grounding, or publishing behavior.
>
> Target: turn the current P1.3 implementation from “colored SaaS sections with entrance animations” into a true five-scene product experience where each stage behaves like a complete canvas and adjacent scenes physically hand off to one another.

---

## 0. Executive summary

The current P1.3 implementation established useful foundations: five stage themes, GSAP integration, responsive layout primitives, reduced-motion support, mobile safe-area handling, and scene-aware colors. However, the actual visual behavior diverges from the intended design in three critical ways:

1. **A stage does not fit in one viewport.** The page stacks `Header + page-intro + StageSceneShell`, while the scene shell itself already reserves nearly one viewport height. This structurally forces document scrolling.
2. **Scene transitions are entrance-only.** React immediately unmounts the old stage when `stage` changes. GSAP then animates only the new stage, with its content initially transparent. The user therefore sees a period of “background color only” before the new content appears.
3. **The interface still contains high-noise meta UI.** The large five-step Stepper, `真实链路 · AI + 知乎检索`, `真实 AI + 知乎检索`, and the explanatory trust line compete with the actual task.

P1.3.1 fixes those issues without changing product logic. The core architectural change is a **double-buffered scene transition host**: during a transition, both the outgoing scene and incoming scene exist simultaneously. The complete outgoing canvas moves left while the complete incoming canvas enters from the right. Only after the transition ends is the outgoing DOM removed.

# 1. Current state

## 1.1 Current page composition

Current `CompilerDemo` renders the page in this order:

```tsx
<main className="app-shell">
  <AppHeader />
  <div className="page-container">
    <section className="page-intro">...</section>

    <StageSceneShell stage={stage} previousStage={previousStage}>
      <StageStepper ... />
      {stage === "input" && <InputStage ... />}
      {stage === "clarify" && <ClarificationStage ... />}
      {stage === "diagnose" && <DiagnosisStage ... />}
      {stage === "coverage" && <CoverageStage ... />}
      {stage === "result" && <ResultStage ... />}
    </StageSceneShell>
  </div>
</main>
```

The scene shell itself uses:

```css
.stage-scene-shell {
  min-height: calc(100dvh - var(--app-header-height));
}
```

This means the page effectively becomes:

```text
Header
+ Intro block
+ spacing
+ almost-one-full-viewport Scene
```

Therefore the main document cannot fit into one screen even before long dynamic content is considered.

### Observable symptom

At desktop viewport sizes, the user must scroll simply to see the lower part of the current stage. This violates the intended five-scene model: each stage should feel like one self-contained screen, not a long webpage section.

---

## 1.2 Current scene transition model

Current stage change logic is immediate:

```ts
function transitionTo(next: QuestionCompilerStage) {
  if (next === stage) return;
  setPreviousStage(stage);
  setStage(next);
}
```

The page content is conditionally rendered from the new `stage` value:

```tsx
{stage === "input" && <InputStage ... />}
{stage === "clarify" && <ClarificationStage ... />}
```

When `stage` becomes `clarify`, React immediately removes the Input DOM. There is no outgoing scene left for GSAP to animate.

Current `StageSceneShell` then animates only the newly mounted scene:

```ts
timeline.fromTo(
  backdrop,
  { xPercent: directionMultiplier * pushPercent },
  { xPercent: 0, duration: sceneDuration },
  0
);

timeline.fromTo(
  mainContent,
  { x: directionMultiplier * 30, opacity: 0 },
  { x: 0, opacity: 1, duration: motionTokens.standard },
  0.46
);
```

### Root cause of the “pure background flash”

The old content is already gone, while the new content deliberately starts at `opacity: 0`. The new backdrop begins animating at `t=0`, but the new content does not begin entering until about `t=0.46s`.

The resulting perception is:

```text
old content disappears immediately
        ↓
only the new scene background is visible
        ↓
new content starts to appear later
```

This is not the desired GSAP panel handoff.

## 1.3 Current duplicated motion layers

The project currently has both:

- GSAP scene animation in `StageSceneShell`
- CSS `.flow-stage` entrance animation

```css
.flow-stage {
  animation: stage-enter 260ms ease both;
}

@keyframes stage-enter {
  from { opacity: 0; transform: translateY(7px); }
  to { opacity: 1; transform: translateY(0); }
}
```

This causes scene-level motion and component-level motion to overlap without a clear hierarchy.

The title reveal itself is desirable; the problem is that the entire content tree can also be fading/moving independently of the full-scene transition.

# 2. Locked goals

P1.3.1 has five non-negotiable goals.

## Goal 1 — One stage, one viewport

On desktop, the active stage must occupy the available viewport below the persistent header.

Target relationship:

```text
Header + Active Scene = 100dvh
```

The document itself must not require normal page scrolling during the primary five-stage flow.

Desktop acceptance targets:

- 1920×1080
- 1440×900
- 1366×768 (compact mode)

At 1440×900 and 1920×1080, all primary task information and the primary action must be visible without document scrolling.

At 1366×768, layouts must switch to a compact density rather than simply overflowing vertically.

For dynamic lists that can exceed available space, secondary detail must be summarized, collapsed, paged, or opened in an overlay/drawer. The main scene canvas must not become a long document.

## Goal 2 — True full-canvas scene handoff

When moving forward:

```text
[old background + old content]  → moves left as one unit
[incoming background + content] → enters from right as one unit
```

When moving backward, direction reverses.

There must never be an intermediate state in which only a flat background color is visible.

## Goal 3 — Preserve useful micro-motion

The user-approved title behavior — e.g. `你真正想问什么？` revealing upward — remains.

Motion hierarchy becomes:

1. **Scene motion:** complete canvas horizontal handoff.
2. **Typography motion:** subtle mask/upward reveal after the incoming canvas becomes visible.
3. **Micro-interaction:** button press/loading, option select, copy success.

Typography motion must never hide the whole content tree.

## Goal 4 — Remove visual noise

Delete completely:

- desktop five-step Stepper
- mobile five-step progress card derived from the same Stepper
- `真实链路 · AI + 知乎检索`
- `真实 AI + 知乎检索`
- `只整理与复制问题，不会自动发布`

Do not replace these with equivalent badges or helper copy.

If stage identity is needed, it may appear only as lightweight editorial metadata, such as:

```text
02 / 05
CLARIFY
```

This is not clickable navigation and must not become another large component.

## Goal 5 — No backend/product logic changes

Do not modify:

- analyze/retrieve/compile APIs
- DeepSeek provider behavior
- domain stage definitions
- clarification semantics
- Zhihu retrieval
- semantic audit / repair flow
- publishable question schema
- clipboard formatting

This phase is visual architecture and interaction only.

# 3. Approaches considered

## Approach A — Keep current single scene and tune animation timing

Example: make `mainContent` appear at `t=0` and shorten the background animation.

### Advantages

- minimal code changes
- low implementation cost

### Rejected because

It cannot animate the outgoing scene because React has already unmounted it. It can reduce the blank-background symptom but cannot produce the requested “old full canvas leaves while new full canvas enters” behavior.

---

## Approach B — Double-buffered outgoing + incoming scene host

During a transition, keep two complete scene canvases mounted:

```text
SceneTransitionHost
├── OutgoingScene
│   ├── Backdrop
│   └── Full stage content
└── IncomingScene
    ├── Backdrop
    └── Full stage content
```

Animate both wrappers in one GSAP timeline.

### Advantages

- exact match to required interaction
- no pure-background frame
- works forward and backward
- preserves React as the business-state owner
- predictable cleanup after transition
- compatible with reduced motion

### Trade-off

Requires separating **business stage** from **currently rendered transition pair**.

### Decision

**Use Approach B.**

---

## Approach C — Browser View Transitions API

### Advantages

- elegant snapshot model
- less manual DOM choreography

### Rejected because

Cross-browser/mobile Safari consistency is not strong enough for this project’s requirements, and the desired behavior is already straightforward with GSAP.

# 4. Target architecture

## 4.1 Split business state from visual transition state

`CompilerDemo` continues to own the real product state:

```ts
stage
analysis
answers
retrieval
compiled
operation
```

The transition layer must not decide product state.

Add a visual host that tracks only presentation state:

```ts
displayedStage
outgoingStage
incomingStage
transitionDirection
isTransitioning
```

Conceptually:

```text
Business state says: "clarify is ready"
        ↓
Transition host receives targetStage=clarify
        ↓
keep displayedStage=input mounted
mount incoming clarify scene
        ↓
animate input → left and clarify → center
        ↓
onComplete:
  displayedStage = clarify
  clear outgoing scene
```

React still decides *what stage is valid*. GSAP only decides *how the visual handoff is shown*.

---

## 4.2 Introduce a stage renderer instead of direct conditional rendering

Current pattern:

```tsx
{stage === "input" && <InputStage ... />}
{stage === "clarify" && <ClarificationStage ... />}
```

Target pattern:

```tsx
function renderStage(stageToRender: QuestionCompilerStage) {
  switch (stageToRender) {
    case "input":
      return <InputStage ... />;
    case "clarify":
      return analysis ? <ClarificationStage ... /> : null;
    case "diagnose":
      return analysis ? <DiagnosisStage ... /> : null;
    case "coverage":
      return retrieval ? <CoverageStage ... /> : null;
    case "result":
      return compiled ? <ResultStage ... /> : null;
  }
}
```

Then the scene host can request both:

```tsx
renderStage(outgoingStage)
renderStage(incomingStage)
```

without duplicating business logic.

---

## 4.3 Refactor `StageSceneShell` into a real transition viewport

Current responsibility is mixed:

- supplies scene variables
- renders backdrop
- performs new-scene entrance animation
- animates headings/content

Target responsibility should be split:

```text
StageTransitionViewport
├── SceneCanvas(stage=outgoing)
└── SceneCanvas(stage=incoming)

SceneCanvas
├── StageBackdrop
└── Stage content
```

### `SceneCanvas`

Pure visual container:

```tsx
<section
  className="scene-canvas"
  data-stage={stage}
  style={sceneStyle}
>
  <StageBackdrop stage={stage} />
  <div className="scene-content">{children}</div>
</section>
```

It should not automatically fade all children in.

### `StageTransitionViewport`

Owns GSAP handoff choreography only.

Forward transition:

```ts
const tl = gsap.timeline({
  defaults: { ease: "power3.inOut" }
});

tl.fromTo(outgoing, { xPercent: 0 }, { xPercent: -100, duration: 0.68 }, 0);
tl.fromTo(incoming, { xPercent: 100 }, { xPercent: 0, duration: 0.68 }, 0);
```

Backward transition:

```text
outgoing: 0 → +100
incoming: -100 → 0
```

Critical rules:

- no root-scene `opacity: 0`
- no gap between the two canvases
- both canvases fill the viewport
- outgoing remains visible until its edge leaves viewport
- incoming is already fully painted while entering
- pointer events belong only to the active/incoming scene during transition
- outgoing scene receives `aria-hidden=true` once transition begins

# 5. Exact transition choreography

## 5.1 API-loading phase

The scene must **not** start moving when the button is clicked.

Example Input → Clarify:

```text
User presses “开始编译问题”
        ↓
button press feedback
        ↓
spinner + “正在理解你的问题…”
        ↓
Input scene stays completely in place
        ↓
Analyze API returns successfully
        ↓
Clarify DOM becomes available
        ↓
start scene transition
```

This preserves a clear mental model: loading belongs to the current stage; movement means the next stage is actually ready.

The same rule applies to:

- Diagnose → Coverage (`retrieving`)
- Coverage → Result (`compiling`)

---

## 5.2 Forward transition timing

Recommended baseline:

| Time | Outgoing | Incoming |
|---:|---|---|
| 0 ms | full scene at x=0 | full scene at x=100% |
| 100 ms | begins moving left | begins entering |
| 340 ms | roughly half gone | roughly half visible |
| 680 ms | fully outside left | fully at x=0 |
| 680–840 ms | removed | headline micro-reveal completes |

The scene motion itself should be approximately **0.62–0.72s**.

Do not delay incoming content opacity. The incoming scene’s content is visible as part of the canvas while it slides in.

---

## 5.3 Typography reveal

After or during the final portion of the canvas movement, the primary headline may use the existing successful upward reveal style.

Recommended values:

```text
y: 18–28px → 0
opacity: 0.65 → 1
start: around 55–65% of scene transition
end: around 100–120ms after scene settles
```

The text reveal should feel like refinement, not a second page load.

Do not animate every paragraph, chip, and label independently.

# 6. One-viewport layout redesign

## 6.1 Remove `page-intro` from the flow

The current top-level intro:

```text
知乎 AI 提问编译器
把模糊需求，整理成值得回答的问题
先把问题问清楚，再进入答案世界。
真实链路 · AI + 知乎检索
```

must no longer occupy a separate block above every scene.

The persistent header should be followed immediately by the scene viewport:

```text
Header
SceneViewport
```

Target CSS model:

```css
.app-shell {
  height: 100dvh;
  overflow: hidden;
}

.scene-transition-viewport {
  height: calc(100dvh - var(--app-header-height));
  overflow: hidden;
  position: relative;

  position: absolute;
  inset: 0;
}
```

No `.page-container` should add enough vertical padding to create document scrolling around the scene.

---

## 6.2 Scene-internal safe frame

Each scene gets an internal safe frame:

```text
SceneCanvas
└── SceneSafeFrame
    ├── lightweight stage meta (optional)
    ├── primary stage content
    └── primary actions
```

Desktop maximum content width remains constrained, but the colored stage background spans the entire scene viewport.

Recommended safe margins:

- desktop 1440+: 40–56px vertical, 64–96px horizontal
- desktop 1366×768 compact: 20–28px vertical
- mobile: 12–20px plus safe area

## 7.2 Clarify

Current four-card grid is visually unbalanced and wastes viewport space.

Change to **single-question focus** within the Clarify stage:

```text
02 / 05 · CLARIFY

你目前的情况更接近哪一种？

[在校学生]
[非技术岗在职]
[技术相关岗位]
```

Benefits:

- no large empty lower-right region
- reduces information overload
- fits one viewport
- provides a clear interaction rhythm
- makes the overall five-scene transition distinct from the within-stage question transition

The user may still skip an uncertain question if the existing business rule permits it.

---

## 7.3 Diagnose

Use a compact split layout:

```text
left: original question + intent summary
right: diagnostics
```

Diagnostics should prioritize the most important issues and fit within the scene. If the generated list exceeds the visual capacity, show the primary items plus a lightweight “更多诊断” overlay instead of extending the document.

---

## 7.4 Coverage

This stage can naturally overflow because evidence count may reach 20+.

The scene should show:

- retrieval status
- coverage summary
- knowledge gaps
- top evidence items (recommended 3–5 depending on viewport height)
- evidence total count
- `查看全部` action

`查看全部` opens a contained overlay/drawer/modal that may scroll internally. The main scene remains fixed to one viewport.

The primary scene must not render all 20+ evidence items into the document height.

---

## 7.5 Result

The visual priority is:

```text
Before → After
```

The publishable result must remain the dominant surface.

Internal IR stays collapsed/secondary.

Primary actions:

- 复制知乎版问题
- 前往知乎

Secondary actions remain visually quieter.

If the publishable context is unusually long, keep the main document fixed; the result surface may use an internal bounded region or expand overlay rather than increasing document height.


The requirement is visual:

```text

DIAGNOSE
```

The existing persistent header can remain because it provides brand and `新建问题`.

However, it should remain visually quiet and consume minimal height.

No additional trust badges, status pills, or stage navigation should be placed in the header.

The header is a stable frame; the scene below it is the moving canvas.

# 10. Motion ownership rules

To prevent the current layered-animation problem, use strict ownership.

## GSAP owns

- full scene horizontal transition
- headline reveal tied to scene transition
- optional scene-number reveal

## CSS owns

- button hover/press
- focus styles
- very small selection feedback
- spinner rotation

## React owns

- stage/business state
- loading state
- data availability
- clarification answers
- retrieval/compile lifecycle
- whether a transition is allowed to begin

### Remove/disable

Generic `.flow-stage` automatic entrance animation for top-level stages.

A stage must not receive an extra generic fade/translate merely because React mounted it.

---

# 11. Concurrency and interaction safety

A transition must be treated as a short visual lock.

During `isTransitioning=true`:

- prevent another stage transition from starting
- disable pointer interaction on outgoing scene
- avoid duplicate API actions
- do not mutate `stage` again until transition completion unless the user triggers a hard reset/new-question action

If a reset occurs mid-transition:

- kill the active GSAP timeline
- clear outgoing/incoming buffers
- render Input directly

GSAP cleanup must remain scoped through `useGSAP` / `gsap.context` semantics.

---

# 12. Reduced-motion behavior

For `prefers-reduced-motion: reduce`, do not perform a full horizontal canvas travel.

Use a short crossfade or immediate swap:

```text
outgoing opacity 1 → 0
incoming opacity 0 → 1
~160ms
```

No background-only frame is permitted even in reduced-motion mode.

---

# 13. Mobile behavior

The mobile product must use the same scene architecture.

Differences:

- horizontal travel may be shortened visually (e.g. 20–35vw) while still reading as a scene handoff
- header uses compact height
- scene safe frame uses `env(safe-area-inset-*)`
- browser document remains fixed to `100dvh`
- if dynamic content cannot fit, only the stage-internal content region may scroll; the document itself should not become a long page

Do not restore the large mobile progress card.

# 16. Performance constraints

Continue following the GSAP performance rules already adopted:

Prefer:

- `transform`
- `opacity`

Avoid scene animation through:

- width/height
- top/left
- layout-heavy properties
- large animated blur/filter stacks

Both canvases exist only for the short transition interval. The outgoing canvas must be removed after completion to avoid retaining duplicate large DOM trees.

---

# 17. Acceptance criteria

P1.3.1 is accepted only if all of the following are true:

1. On 1440×900 and 1920×1080, every normal stage’s primary information and primary action are usable without document scrolling.
2. The large five-step navigation is absent from the main product UI.
3. The intro trust badge and Input trust line are absent.
4. During every forward stage transition, the complete outgoing scene visibly moves left while the complete incoming scene simultaneously moves in from the right.
5. During backward navigation, the direction reverses.
6. No transition frame shows only a flat background color with missing content.
7. API loading occurs while the current scene remains stable; scene movement begins only when the next stage data is ready.
8. Headline upward reveal remains subtle and secondary to the full-canvas motion.
9. Clarify no longer renders an unbalanced 4-card wall; it uses focused question presentation.
10. Coverage does not expand 20+ evidence rows into the main page height.
11. Reduced-motion mode remains fully functional.
12. Existing AI/API/Domain/Zhihu/P1.2 behavior remains unchanged.
13. Web tests, Domain tests, typechecks, production build, and viewport smoke checks are green.

- changing the five stage colors unless separately approved
- redesigning brand/logo
- adding ScrollTrigger to the product flow
- adding 3D/WebGL
- Companion extension
- Expo Android client
