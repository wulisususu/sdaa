# P1.3.2 Return-safe Zhihu Handoff & Session Recovery Design

> Status: **Design only**. This document defines a separate UX refinement stream that can be implemented by a second agent without changing AI, API, Domain, Zhihu retrieval, compile, semantic-grounding, or publishing behavior.
>
> Primary goal: after a user generates a publishable question and opens Zhihu, the Ask Better experience must remain easy to recover even for users who do not know browser back shortcuts, tab navigation, or how to re-enter the site URL.
>
> Visual principle: **no explanatory helper copy when a concise icon + short action label can communicate the behavior.** No emoji icons. No tiny helper text. The action area should feel like a clean product toolbar, not an instruction sheet.

---

## 0. Executive summary

The current Result flow already opens `https://www.zhihu.com/` with `_blank`, so the original Ask Better tab is normally preserved. However, the UI does not communicate this cleanly, there is no local recovery if the Ask Better tab is closed, and the result action area contains long labels and helper copy that conflict with the desired minimal visual language.

P1.3.2 introduces three coordinated improvements:

1. **Minimal result actions** — replace long CTA labels and helper copy with concise actions plus a consistent thin-line icon system.
2. **Return-safe handoff** — opening Zhihu preserves the current Ask Better result and explicitly persists the completed session before handoff.
3. **Completed-session recovery** — if the user later opens Ask Better again, the latest valid completed result can be restored from `localStorage` for a limited TTL, without requiring browser history knowledge.

This phase deliberately does **not** attempt to automate Zhihu, fill Zhihu forms, detect login state, control browser tabs, or publish questions.

---

# 1. Current state

## 1.1 Current Zhihu handoff behavior

`CompilerDemo` currently opens Zhihu with:

```ts
function handleOpenZhihu() {
  window.open("https://www.zhihu.com/", "_blank", "noopener,noreferrer");
}
```

This has one useful property already:

```text
Ask Better tab remains open
        +
Zhihu opens separately
```

But this alone does not solve the user experience for people who:

- do not understand browser tabs;
- close the Ask Better tab accidentally;
- open Zhihu in an external app and later return to the browser;
- manually revisit `ask.wulisu.icu` and expect the previous result to still exist.

There is currently no persistence layer for the completed result.

---

## 1.2 Current result action UI is too verbose

Current `CompiledQuestionPanel` renders actions equivalent to:

```text
复制知乎版问题
前往知乎 ↗
重新优化
```

and then adds helper copy:

```text
复制后前往知乎发起提问
```

`ResultStage` separately adds:

```text
还想整理另一个问题？
新建一个问题
```

This creates two problems:

1. the action area repeats intent in full sentences rather than acting like a compact toolbar;
2. helper copy adds visual noise even though the actions can be communicated with icons and short labels.

The current Result action system should therefore be simplified, not expanded with additional “welcome back” or “how to return” instructions.

---

## 1.3 Current copy feedback is text-heavy

Current copy state labels are:

```text
复制知乎版问题
✓ 已复制
复制失败，请重试
```

For the desired visual language, this should become:

```text
[Copy icon] 复制
[Check icon] 已复制
[Copy/Retry icon] 重试
```

The state remains fully understandable while removing excess wording.

---

## 1.4 No local recovery state exists

Repository search currently finds no `localStorage`, `sessionStorage`, `visibilitychange`, or equivalent persistence/recovery implementation in the Web flow.

Therefore a user who closes the Ask Better tab loses the in-memory React state even though a completed compile already exists.

The product should recover the **latest completed session**, not attempt to serialize every transient loading state.

# 2. Locked UX decisions

## 2.1 No explanatory small text in the handoff/recovery UI

The following patterns are prohibited in this feature:

```text
“知乎会在新标签页打开，本页会保留。”
“复制后前往知乎发起提问。”
“欢迎回来，你可以继续……”
“检测到你上次还有一个未完成的问题……”
```

Do not replace these with smaller grey text.

Behavior is communicated through:

- icon;
- concise action label;
- familiar layout hierarchy;
- native browser behavior.

No `small` element should be introduced inside the new handoff/recovery action module.

---

## 2.2 Result actions use concise labels only

Locked labels:

```text
复制
打开知乎
继续优化
新问题
```

Copy state labels:

```text
已复制
重试
```

Recovery action labels:

```text
继续上次
新问题
```

Do not expand these back into sentence-length CTA text.

---

## 2.3 Buttons require a coherent icon language

Use thin, rounded, stroke-based icons with the same visual geometry.

Required semantic mapping:

| Action | Icon concept |
|---|---|
| 复制 | Copy |
| 已复制 | Check |
| 打开知乎 | ExternalLink |
| 继续优化 | WandSparkles / Sparkles |
| 新问题 | Plus / SquarePen |
| 继续上次 | History |
| 重试 | RotateCcw / Copy |

Rules:

- no emoji;
- icon uses `currentColor`;
- recommended size: 18px desktop/mobile;
- recommended stroke width: ~1.8;
- rounded caps/joins;
- labels must remain visible; do not make icon-only primary actions;
- icon is decorative when the visible text already names the action (`aria-hidden="true"`).

### Dependency decision

Do **not** add a new icon package only for these six icons.

Create a tiny local icon primitive/component set using inline SVG paths. This avoids adding `lucide-react`, keeps the dependency surface unchanged, and gives the project exact control over stroke weight.

Suggested file:

```text
apps/web/src/components/action-icons.tsx
```

```text
[ final publishable content ]

  WandSparkles 继续优化       Plus 新问题
```

Hierarchy:

### Primary

```text

```

This remains the dominant CTA because the current product cannot directly publish to Zhihu.

### Secondary

```text

```

This opens the verified root destination in a separate browsing context.

### Quiet actions

```text
WandSparkles 继续优化
Plus 新问题
```

These should use ghost/quiet styling and must not compete with Copy/Open Zhihu.

### Remove

Delete from the Result action area:

```text
复制后前往知乎发起提问
还想整理另一个问题？
```

Do not add replacement helper copy.

# 4. Return-safe handoff behavior

## 4.1 Preserve current browser behavior

The product should continue opening:

```text
https://www.zhihu.com/
```

Do not restore the removed `/question/ask` path and do not claim a direct ask-page deep link exists.

The target should remain a separate browsing context (`_blank`) with `noopener,noreferrer`.

---

## 4.2 Persist before handoff

Immediately before opening Zhihu, write the latest completed session to local storage synchronously.

Conceptually:

```ts
function handleOpenZhihu() {
  saveCompletedSession(currentCompletedSession);
  window.open("https://www.zhihu.com/", "_blank", "noopener,noreferrer");
}
```

This means even if the user later closes the Ask Better tab, the completed result is recoverable.

Do not block opening Zhihu if local storage is unavailable. Persistence failure is non-fatal.

---

## 4.3 No “welcome back” popup

Do not show a modal, toast, banner, or explanatory paragraph when the user returns from Zhihu.

The Result page already contains:

```text
继续优化
新问题
```

Those actions are sufficient.

Optional micro-motion is allowed when the page regains focus, but it must be purely visual and should not require tracking a complex return-state machine. This is not a requirement for P1.3.2.

---

# 5. Completed-session persistence model

## 5.1 Scope: persist completed sessions, not every transient state

P1.3.2 should persist only a session that has reached a successful compiled result.

Do not persist:

- active network operations;
- spinner state;
- API errors;
- transition animation state;
- partially entered raw text before a compile exists;
- unfinished clarification flows.

This keeps recovery deterministic and avoids restoring impossible intermediate UI states.

---

## 5.2 Storage key and version

Use a versioned key:

```ts
const COMPLETED_SESSION_STORAGE_KEY = "ask-better:completed-session:v1";
```

Stored envelope:

```ts
interface StoredCompletedSessionV1 {
  version: 1;
  savedAt: number;
  rawQuestion: string;
  answers: ClarificationAnswers;
  analysis: QuestionAnalysis;
  retrieval: RetrieveResult;
  compiled: CompileResult;
}
```

The existing Domain already exports schemas for:

- `QuestionAnalysisSchema`
- `ClarificationAnswersSchema`
- `RetrieveResultSchema`
- `CompileResultSchema`

Use those schemas to validate restored JSON. Do not trust arbitrary localStorage content just because it parses.

---

## 5.3 TTL

Recovery lifetime:

```text
24 hours
```

Reasoning:

- long enough for a user to leave for Zhihu and return later;
- short enough to avoid surfacing old personal question context indefinitely;
- simple mental model;
- avoids adding account/history infrastructure.

If `Date.now() - savedAt > 24h`, treat the record as expired and delete it.

No user-visible expiry message is needed.

---

## 5.4 Persistence failures are silent and non-blocking

`localStorage` may fail because of browser privacy mode, disabled storage, quota issues, or corrupted data.

All storage functions must fail closed:

```ts
load → null
save → false
clear → best effort
```

No storage error should block:

- compile;
- copy;
- opening Zhihu;
- starting a new question.

Do not show technical storage errors to users.

---

# 6. Recovery experience

## 6.1 Initial-page recovery entry

When the site opens and a valid, unexpired completed session exists, show a compact recovery surface on the Input stage.

It should not be a modal and should not contain explanatory helper copy.

Recommended composition:

```text
[ History icon ]  继续上次
现在转码还有前途吗？

[继续上次]   [新问题]
```

The previous raw question is content, not helper text. It may be truncated to one line visually.

No paragraph such as “检测到上次记录” is allowed.

---

## 6.2 Restore action

`继续上次` restores the completed business state:

```text
rawQuestion
answers
analysis
retrieval
compiled
stage = result
maxVisited = result (if still used by current architecture)
copyStatus = idle
operation = idle
error = null
```

The visual scene system then renders Result using normal current architecture.

Do not restore stale animation/transitional state.

If P1.3.1 has replaced `StageSceneShell` with a transition viewport, recovery should enter Result as a stable initial scene rather than animate through all five scenes.

---

## 6.3 New-question action

Explicitly choosing `新问题` clears the persisted completed session and starts a clean Input state.

This applies to:

- the Result action;
- the recovery surface on initial load;
- the persistent header’s new-question action if that action remains in P1.3.1.

“New question” is an intentional reset, so clearing the old recovery record is correct.

---

## 7.3 `apps/web/src/components/compiler-demo.tsx`


## 7.4 New `apps/web/src/lib/completed-session-storage.ts`

This file owns all browser storage behavior.

Suggested public interface:

```ts
export const COMPLETED_SESSION_STORAGE_KEY = "ask-better:completed-session:v1";
export const COMPLETED_SESSION_TTL_MS = 24 * 60 * 60 * 1000;

export interface StoredCompletedSessionV1 {
  version: 1;
  savedAt: number;
  rawQuestion: string;
  answers: ClarificationAnswers;
  analysis: QuestionAnalysis;
  retrieval: RetrieveResult;
  compiled: CompileResult;
}

export function saveCompletedSession(
  session: Omit<StoredCompletedSessionV1, "version" | "savedAt">
): boolean;

export function loadCompletedSession(now?: number): StoredCompletedSessionV1 | null;

export function clearCompletedSession(): void;
```

Validation should use a Zod envelope composed from existing Domain schemas.

The module must guard `typeof window === "undefined"` because Next.js rendering/tests may execute without a browser.

# 8. Visual specification

## 8.1 Button typography

Do not use tiny action labels.

Recommended minimums:

```text
desktop action label: 14px
mobile action label: 15px
recovery question: 14–16px
icon: 18px
```

Avoid 9–11px explanatory text in this feature.

---

## 8.2 Button shapes

Keep the project’s rounded geometry, but simplify hierarchy.

Recommended:

```text
Primary Copy:
solid / strongest contrast

Open Zhihu:
outlined or light surface

Continue optimize / New question:
ghost / quiet
```

Icons sit immediately left of the label with ~7–8px gap.

No oversized pills, gradient glow, or decorative badge around these actions.

---

## 8.3 Mobile result actions

On narrow screens, avoid four equally heavy stacked buttons.

Preferred layout:

```text
[ Copy 复制          ]
[ External 打开知乎  ]

[ Sparkles 继续优化 ] [ Plus 新问题 ]
```

The first two may be full-width. The quiet pair may share one row when space allows.

Respect safe-area padding from P1.3.1.

# 9. Recovery data flow

## Successful compile

```text
Compile API succeeds
      ↓
set compiled result
      ↓
build completed-session envelope
      ↓
save to localStorage (best effort)
      ↓
show Result normally
```

## Open Zhihu

```text
user clicks ExternalLink + 打开知乎
      ↓
refresh completed-session save synchronously
      ↓
open https://www.zhihu.com/ in _blank
      ↓
Ask Better tab remains intact
```

## User closes Ask Better and later returns

```text
Ask Better loads
      ↓
loadCompletedSession()
      ↓
JSON parse
      ↓
version + TTL + Zod validation
      ↓
valid?
  ├─ no → delete/ignore → normal Input
  └─ yes → show compact ResumeSessionCard on Input
```

## Resume

```text
click History + 继续上次
      ↓
hydrate business state
      ↓
render Result as stable scene
```

## New question

```text
click Plus + 新问题
      ↓
clearCompletedSession()
      ↓
reset existing business state
      ↓
Input
```

# 10. Parallel-work protocol with the P1.3.1 agent

This requirement is critical because P1.3.1 is currently modifying scene architecture while this feature touches some of the same Result/Compiler integration points.

## 10.1 Branch budget

At the time this design is written, remote branches include:

```text
main
feat/core-pipeline
feat/deployment-smoke
feat/p1.3-five-scene
```

The older `feat/p1.3-five-scene` has already been merged into `main` and should be deleted after verifying its commits are reachable from `main`. This frees a branch slot before both P1.3.1 and P1.3.2 temporary branches are simultaneously active.

Do not exceed the project rule of **5 total active branches including `main`**.

## 10.2 Parallel-safe work

The P1.3.2 agent may safely implement these new files without touching P1.3.1 scene code:

```text
apps/web/src/lib/completed-session-storage.ts
apps/web/src/lib/completed-session-storage.test.ts
apps/web/src/components/action-icons.tsx
apps/web/src/components/resume-session-card.tsx
apps/web/src/components/resume-session-card.test.tsx
```

It may also prepare isolated tests for result action labels/icons if they do not force stale snapshots of files that P1.3.1 is actively rewriting.

## 10.3 Integration-sensitive work

These files are likely to overlap with P1.3.1:

```text
apps/web/src/components/compiler-demo.tsx
apps/web/src/components/result-stage.tsx
apps/web/src/components/compiled-question-panel.tsx
apps/web/src/app/globals.css
```

Before editing these files, the P1.3.2 agent must:

The new agent must never revert the one-viewport/double-buffer scene work from P1.3.1.

# 11. Testing strategy

## 11.1 Storage unit tests

Required cases:

- saves valid completed session;
- loads valid unexpired session;
- rejects expired session and clears it;
- rejects malformed JSON;
- rejects schema-invalid JSON;
- rejects unsupported `version`;
- returns null server-side when `window` is unavailable;
- storage exception does not throw to caller.

Use deterministic injected `now` for TTL tests.

---

## 11.2 Result action tests

Update existing publishable CTA tests to assert:

```text
contains: 复制
contains: 打开知乎
contains: 继续优化
contains: 新问题

not contains: 复制知乎版问题

not contains: 还想整理另一个问题？
```

Also assert icon hooks/names exist without relying on exact SVG path strings.

Do not remove the existing safety assertion that the product never claims:

```text
一键发布
```

## 11.3 Recovery component tests

Verify:

- recovery card renders only when a valid completed session exists;
- displays the previous raw question;
- `继续上次` calls resume;
- `新问题` clears/discards;

---

## 11.4 Integration regression

Existing behavior must remain green:

- compile result generated normally;
- copy still writes the exact formatted publishable question;

- no `/question/ask` regression;
- continue optimize works;
- new question resets state;

- no backend API change.

# 12. Acceptance criteria

P1.3.2 is accepted only if all of the following are true:

1. Result actions visibly use icons plus the concise labels `复制 / 打开知乎 / 继续优化 / 新问题`.
2. Copy success becomes icon + `已复制`; copy failure becomes concise `重试`.
3. `复制后前往知乎发起提问` is absent.
4. `还想整理另一个问题？` is absent.
5. The handoff/recovery module introduces no explanatory small-print text.
6. Clicking `打开知乎` keeps the existing verified root destination and opens separately.
7. A completed session is persisted before handoff on a best-effort basis.
8. Closing/reopening Ask Better within 24 hours can surface `继续上次` for the latest valid completed result.
9. Restoring the session returns directly to a stable Result state; it does not replay API calls or five scene transitions.
10. Explicit `新问题` clears the stored completed session.
11. Corrupted/expired localStorage never crashes or blocks the product.
12. No account, Zhihu cookie, token, API key, or credential is stored.
13. No direct-publish or Ask deep-link claim is introduced.
14. P1.3.1 scene continuity/one-viewport behavior is preserved after integration.
15. Web tests, typecheck, production build, and mobile/desktop smoke checks pass.

---

# 13. Scope boundary

This phase does **not** include:

- browser extension / Companion;
- automatic Zhihu form filling;
- detecting Zhihu login status;
- controlling or closing the Zhihu tab;
- direct question publishing;
- cloud account/session history;
- cross-device sync;
- persistent history list of multiple old questions;
- mid-flow autosave before a completed compile exists;
- changing AI prompts or retrieval behavior;
- changing P1.3.1 scene colors/transition architecture.

The objective is intentionally narrow:

> **Make the final Result handoff concise, icon-led, recoverable, and safe for users who do not understand browser navigation — without adding instructional clutter.**
